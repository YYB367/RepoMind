# 阶段目标

帮助新用户使用 V4.3.1 本地网页工作台：启动服务、检查环境、执行真实开发任务、核对文件修改和版本证据、由用户审核候选，再用独立新任务验证召回。本指南由 2026-11-09 的真实试用任务生成，2026-11-14 核对后纳入 V4.3.1，并补充运行反馈。

日常流程是：**任务 → 检查环境与相关记忆 → 启动开发任务 → 核对修改与证据 → 用户确认 → 下一任务验证召回**。候选可以为空；没有实际文件证据时，不必为了完成流程制造记忆。

## 启动工作台

在 PowerShell 中运行，保持终端打开。本工作区使用下列已有测试解释器，无需重新创建环境：

~~~powershell
Set-Location 'D:/software/codex/2026-10-26/1-repomind-codex-md-2-repomind/outputs/RepoMind'
$python = 'D:/software/codex/2026-10-26/1-repomind-codex-md-2-repomind/work/v2-venv/Scripts/python.exe'
$env:PYTHONPATH = 'src'
& $python -m repomind --db work/v4.0/pilot.sqlite3 web --project RepoMind --root . --port 8768
~~~

打开启动输出中的 [任务工作台](http://127.0.0.1:8768/tasks)。顶部还有 [待确认](http://127.0.0.1:8768/review?project=RepoMind)和 [项目记忆](http://127.0.0.1:8768/memories?project=RepoMind)。使用 `127.0.0.1` 地址，网页服务仅供本机单用户使用。

`--db` 指向任务、候选和正式记忆共用的 SQLite 账本；`--project` 指定项目名，`--root .` 将当前仓库登记为该项目的任务目录。以后继续使用同库、同项目，才能保留并召回已有记忆。启动任务服务会按需创建数据库和任务表；检查已有记录时优先使用已运行的服务。

出现“同一记忆库已有任务服务”时，使用已有工作台，或在原服务终端按 Ctrl+C 停止后再启动。换端口不能解除同库服务锁，不要删除锁文件或数据库。仅端口被其他程序占用时，才更换 `--port` 并相应修改浏览器地址。多项目登记和全新环境安装见 [V4.3 启动说明](v4.3-delivery.md#启动与操作步骤)，此处不重复旧版 V2 实验环境命令。

网页无需 npm，也不要求先启动旧版 Docker 基准实验。运行开发任务需要服务终端能找到已安装、已登录的 Codex CLI；使用本机 Codex 配置、登录与额度，网页没有填写聊天 API Key 的入口。密钥只从本机环境变量读取，不写入任务需求、源码或报告。

## 检查环境与相关记忆

在“任务”页选择 `RepoMind`，输入实际开发需求，说明范围、期望结果和必要的验证。例如可要求核对某份已有文档并修正过时步骤，而不是预先编写要记住的答案。只需输入需求，无需填写事实键、值或引文；需求上限为 8000 字符。

点击“检查环境与相关记忆”，核对“运行环境”中的六项结果：

| 页面检查项 | 应核对的内容及失败处理 |
| --- | --- |
| 项目目录 | 是否为要修改的仓库。登记错误时在终端修正 `--root` 或项目配置后重启；网页不能指定任意宿主目录。 |
| Git | 所选目录是否正好为 Git 仓库根目录；从仓库根目录启动服务。 |
| Python | 是否显示上述测试解释器。若不符，停止服务，用正确解释器重启。 |
| Codex CLI | 服务终端是否能找到 `codex` 并取得版本；安装或调整 PATH 后重启服务。 |
| Codex 登录 | 是否已登录；在同一终端核对 `codex login status`，需要时完成登录，再重新预查。页面不显示凭据。 |
| 读写沙箱 | workspace 沙箱能否在登记项目中完成临时文件读写；失败时在同一终端检查 Codex 沙箱错误，修复后重新预查。 |

预查不调用模型，但会保存一条“等待启动”的任务记录，并在项目 `work` 目录进行临时读写探测。因此点击预查也有本地状态写入；单纯浏览已有任务不执行预查。全部检查通过后，“启动开发任务”才可用。预查成功只说明启动条件满足，不保证模型一定完成需求。

在“相关已确认记忆”中展开条目，核对事实键（页面显示 `subject / field`）、值、来源路径和来源 ID。没有相关记忆时，页面提示“未找到相关已确认记忆。任务仍可启动。”，首次使用可正常继续。

修改开发需求或切换项目后，需要重新预查。审核使相关已确认记忆发生变化时，启动会提示重新预查；重新检查并核对后再启动。

## 执行任务与验收结果

点击“启动开发任务”才会调用模型。后台为本次需求启动独立的 Codex `workspace-write` 会话，可在所选项目内修改文件。包装器要求保留已有未提交改动和冻结数据，不提交 Git，不编辑记忆库或执行审核命令；实际文件权限仍由 Codex 沙箱控制。

页面会轮询状态：“排队中”→“Codex 正在执行”→“会话已结束”，也可能显示“执行失败”“上次运行中断”或“运行已停止”。同库只允许一个活动任务；提示已有任务运行时，等待它结束。重复点击不会重复执行同一任务。

任务结束后依次检查右侧的“助手结果”“本次文件修改”和“记忆候选”，并记录页面显示的任务 ID 与“独立会话”ID。“会话已结束”表示包装器收到完整会话结果，不能代替需求验收；工具失败提示、实际 diff 和必要的测试结果都要核对。失败任务也可能已经留下部分文件修改。

“最近任务”可以重新打开历史结果，不会重跑模型。要执行新的需求，重新填写需求并预查、启动；打开旧任务不算独立新任务。网页显示运行反馈和有上限的脱敏命令事件，不是交互终端，也没有自动重试或撤销文件修改按钮。任务执行上限为 30 分钟；停止服务会请求终止正在执行的 Codex。异常退出或中断后先核对遗留进程与文件，再决定是否重新执行，服务不会自动重跑。

## 查看修改与文件预览

在“本次文件修改”中点击文件名，展开 `added`（新增）、`modified`（修改）或 `deleted`（删除）的差异。`before/` 是任务启动前，`after/` 是结束后的版本；`-` 行为删除，`+` 行为增加。这里比较任务前后快照，保留任务开始前已有的改动，不等同于 `git diff HEAD`。同一项目同时被其他进程修改时，外部变化仍可能混入，应串行操作。

点击任务结果中的候选链接，进入该项目“待确认”详情。右侧“来源文件预览”显示候选绑定的版本，黄色高亮为支持该候选的确切引文。点击“显示完整正文”与“仅显示引文前后文”切换范围；展开“本次任务差异：文件路径”可查看关联任务的各文件差异。“重新读取来源”只重试预览，不重新执行任务。

| 预览标签 | 如何理解 |
| --- | --- |
| 任务结束快照 | 使用与候选摘要一致的任务结束版本；工作区后来改变时，仍展示该历史产出。 |
| Git 提交版本 | 从候选绑定的提交读取文件，核对显示的提交与摘要。 |
| 当前文件（摘要匹配） | 无可用任务快照时，当前文件字节摘要与候选来源相同才展示全文。 |
| 仅保存引文 | 无法完整读取或验证正文，只展示已保存的引文；不能据此声称已核对完整文件。 |

当前只预览 UTF-8 的 `.md`、`.py`、`.json` 和 `.txt`，按纯文本显示，不渲染 Markdown 或执行 HTML。路径限现有 ASCII 规则，中文文件名暂不支持；隐藏、凭据及工作状态目录等路径受排除规则限制。单文件正文上限 256 KiB，单次快照正文预算 4 MiB，最多检查 5000 个路径。其他类型或超限文件可能出现在清单中，但没有完整正文差异；网页也不是任意文件浏览器，无候选时可在本地编辑器查看文件。

预览失败时先看警告，可点击“重新读取来源”。预览读取失败不会清除当前候选和未保存编辑；刷新整个列表或离开页面则可能放弃编辑，需按提示处理。摘要与引文匹配证明版本一致，事实含义是否受原文支持仍需用户判断。完整规则见 [V4.3 文件预览规则](v4.3-delivery.md#文件预览规则)。

## 由用户审核候选

从任务候选链接进入最容易定位到对应记录；也可在“待确认”页选择同一项目和“待确认”状态，点击“查询”或“刷新记录”。状态可切换为“已确认”“已拒绝”“全部记录”。

逐条核对事实内容、事实键、记录类型、生效时间、助手提取理由，以及“原文证据”和预览正文。展开“查看来源标识与摘要”，检查来源路径、来源类型、Git 提交（如有）、SHA-256、候选 ID、来源 ID 与审核版本。候选应来自实际文件产出，引文不能仅在字面上匹配却不支持所写结论。

需要调整时可编辑“事实内容”“记录类型”（声明事实／计划／已完成）和“生效时间（含时区）”，先点击“保存修改”，再核对保存后的内容与版本。项目、事实键和来源不能在此修改；这些信息错误时拒绝该候选，后续依据正确文件证据重新提出。

由用户点击“确认写入”，在弹窗中核对项目、事实键、值、审核版本与路径，最后点击“确认写入正式记忆”。暂不确定时点击“返回核对”；不接受时点击“拒绝候选”，再在弹窗点击“确认拒绝候选”。确认、拒绝均保留审核历史，已拒绝记录不能直接改为确认。提示“记录已变化”时刷新并重新审核。开发助手不得替用户确认。

进入“项目记忆”页，选择同一项目及适当的“事实日期（UTC）”，点击“查询”，核对有效事实及来源。可选“获知日期（UTC，可选）”限制系统当时已收到的记录；日期均取 UTC 当日结束。这里可能显示“有效事实”“仅有计划”或“事实冲突”，后两者不能当作已经成立的唯一事实。

没有候选并不表示任务失败；查看实际文件和助手结果，判断是否有值得长期保存的事实。候选生成只进入待审队列，未经用户确认的新候选不会被后续任务召回。

## 在下一任务中验证召回

先确认目标候选已经由用户审核为“已确认”，在“项目记忆”中核对它在当前时间有效。记下真实的 `subject / field` 和来源 ID，不要复制候选值或原文到新需求中。

回到“任务”页，保持同一数据库服务和项目，输入一个要求应用该事实的后续需求。例如将下面占位符替换为刚确认的真实事实键：

> 根据项目中已确认的 `<subject> / <field>` 约定，解释下一步应怎样操作，并引用记忆来源。本次只解释，不修改文件。

点击“检查环境与相关记忆”。应在“相关已确认记忆”看到目标键和值，展开后核对路径和来源 ID；这说明当前需求已匹配到该事实。然后点击“启动开发任务”，检查结果中的“独立会话”ID 与上一任务不同，并核对助手是否正确应用该事实、引用对应来源。网页启动仍使用 `workspace-write`；“不修改文件”是任务要求，不是切换到工具级只读模式。

需要进一步核查时，可只读打开以下本地接口，把 `<任务ID>` 换成结果面板显示的实际 `task-…` ID：

~~~text
http://127.0.0.1:8768/api/tasks/<任务ID>?project=RepoMind
~~~

`recalled` 是预查选中的事实，`result.recalled` 是实际传给包装器的事实；其中包含 `subject`、`field`、`value`、`source_id`、`path` 和可选的提交信息。`result.session_id` 与 `result.assistant_message` 可核对独立会话和回答。启动时会重新比较相关记忆是否变化，变化则要求重新预查，保证使用已核对的事实列表。日常验证不必操作数据库或运行审核命令。

预查出现目标事实只能证明检索匹配；实际注入列表及回答中的正确应用、引用共同支持“新会话使用了该证据”。仅仅回答相似不能证明跨会话召回成功。召回为空时依次核对同库同项目、审核状态、生效时间及冲突状态，再在需求中写出准确事实键。当前按任务词匹配，最多选择四条且受 3200 字节上下文预算限制，同义改写或相关事实过多时可能漏选。

终端包装器和回执的详细操作可参考[V4.0 包装器流程](v4.0-delivery.md)；网页任务不需要再手工运行一次包装器，也不依赖原生 hooks 自动触发。

## 原理、限制与本次核对

本地 Python HTTP 服务直接提供页面与 JSON，适合当前单机工作台，无需另建前端服务。后台线程复用 Codex 包装器，每任务独立会话；SQLite 保存任务、候选和正式事件，共用审核事务与版本校验。任务前召回已确认的有效事实，任务后按文件引文校验候选，用户确认后才写入正式记忆。受限文本快照与 Git 版本帮助用户核对原始产出。设计比较、兼容和回滚取舍见 [ADR 0027](decisions/0027-web-tasks-and-versioned-evidence.md)。

原始 2026-11-09 文档任务仅补充指南和入口链接。V4.3.1 新增活动记录表及流式命令反馈，迁移、限制与回滚见 [V4.3.1 交付](v4.3.1-delivery.md)。默认 reference、原始任务回执、候选来源快照和冻结数据保留。

核对日期：2026-11-09。命令参数已使用指定解释器的 `python -m repomind web --help` 核对；页面名称与操作按当前 `tasks.html`、`tasks.js`、`index.html`、`app.js` 及 `server.py`、`tasks.py`、`evidence.py`、`codex_flow.py` 核对。当前 8768 工作台已运行，本次只读检查已有页面与接口，不启动预查、开发任务或审核操作，不修改记忆数据库。

本次只读检查通过：三张页面及两份脚本的 HTTP 返回与当前源码一致（页面动态授权标记除外）；两份已结束任务回执及一份候选预览的字段与本文对应；七处本地文件链接目标均存在。浏览器自动化先因临时目录不可写而失败，改用工作区内通信目录后仍未能建立浏览器连接，因此本次没有新增点击验收；涉及预查、启动、保存和确认的动作依据当前实现核对。

本次文档核对不代表新增真实模型、准确率或成本验收。已有真实两会话、浏览器和回归证据见 [V4.3 交付](v4.3-delivery.md#真实验收证据)、[浏览器检查记录](../reports/v4.3/browser-checks.json)与 [最终验收报告](../reports/v4.3/acceptance-final.json)，与本次只读核对区分。

## V4.3.1 运行反馈

点击“最近任务”查看结果顶部的“运行反馈”。“已运行”从开始时间计时，运行中每秒更新，结束后固定；“最近活动”来自真实执行事件，不因进程检查而刷新。长命令静默时，可以同时看到最近一次事件和进程检查时间，不能仅据此认定卡住或任务完成。

展开“失败记录与后续执行”，查看脱敏命令、原始退出码和失败输出摘录。后续完全相同命令成功时，首次失败仍保留，并单独显示同命令后续成功。修改参数、路径或环境后的调用无法自动认定为重试；命令成功也不代表开发需求验收通过。“命令记录”可查看后续执行。

旧任务只记录退出码时会显示“旧版未记录命令/原因”，不补造证据。失败输出和命令有长度、事件数限制，超过限制明确提示；不要把密码或其他私人内容写入任务或命令。脱敏覆盖常见凭据格式、授权头及服务进程已配置的密钥值，不能自动识别所有私人自然语言。

Codex 发现顺序为 REPOMIND_CODEX_EXECUTABLE 指定的存在的绝对路径、当前 PATH、Windows Desktop 当前安装目录中的最新程序。可在启动服务前设置 $env:REPOMIND_CODEX_EXECUTABLE = 'C:/实际目录/codex.exe'；显式配置失效时应修正配置，系统不会悄悄换程序。程序路径或启动检查失败时，登录显示“尚未检查”，先修复路径再预查，无需重新填写 API Key。

本版验收未新增模型调用。历史页面只验证已有记录，模拟事件与真实容器回归分别记录，详见本版交付和验收报告。
