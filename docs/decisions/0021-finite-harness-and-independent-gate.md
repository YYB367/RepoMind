# 阶段目标

将历史轨迹反馈转成有限候选，通过独立验证判断是否推荐改用新 Harness。

## 原方案和变更

V2 每次模型请求发送已有工具会话，写入源码会在历史动作里保留完整正文。模型自行在有限回合内完成验证和收尾。历史记录显示，即便最终代码通过，也有运行因未提交 finish 而失败。V3 将重复写入回显与收尾节奏作为独立试验变量。

压缩策略只在给模型的历史消息中替换已经提交给工具的写入正文。工具接收原始动作，审计记录保留原文，模型也可用 read_file 取得当前文件。这样减少重复前缀，但模型可能需要额外读取。收尾提示使用已执行的公开测试与非空 diff，且两者须发生在最后一次写入之后。它只提示模型何时结束，严格完成仍由正常 finish、文件变更及最终双重测试共同判定。

## 为什么用有限枚举和本地锁

两个开关可以完整枚举，单项候选便于区分作用，组合候选可以发现交互。在已知上限内直接跑开发任务，比开放式让模型改执行器更易审计。另一选择是将旧模型动作强行代入新提示来打分，这能检查动作兼容性，无法回答新提示会让模型生成什么。因而历史只用来提名，人工参考解只验工程，实际效果重新调用模型。

开发报告和锁文件通过 SHA-256 绑定到实现、协议、预算、模型配置与镜像。保留集只接受符合锁的候选，验证前不会读取保留题与判题。哈希能发现本地文件意外改动，依赖可信执行者与冻结提交。两轮使用同四道新题，便于核查随机波动，样本数仍是四道。

## 兼容、迁移和回滚

新增 harness-tune 和 harness-validate。原 Agent 路径使用默认参数，SQLite 数据与原报告无需迁移。实验新目录保存每项结果，重复执行使用新目录。报告给出建议，运行既有 agent-bench 即继续使用原流程。旧的 v2.1.0 wheel 和 Git 标记可用于回滚程序。

## 研究来源

候选探测和组合借鉴 Harness²。对已观察轨迹的复用借鉴 Dream-RSI。这里用固定规则和小规模合成判题检验可复现性。[Harness²](https://arxiv.org/abs/2610.14224) · [Dream-RSI](https://arxiv.org/abs/2609.14858)
