# 阶段目标

让真实项目的证据经过显式审核后进入同一个 SQLite 事件账本，并能复查审核和来源。

## 选型与原因

原有 import 接收已决定的结构化事件。V1.1 的 ingest 能提取并落盘候选文件，显式 apply 可批量导入。真实项目需要独立保留待确认、拒绝和修改后的决定。新增审核队列，复用原 Event、来源信封、正式写入校验和双时间查询。

命令行接收操作者标注的事实键、值、事件类型和原文片段。程序只读取指定文件或指定 Git 提交中的文件，验证确切引用，记录路径、提交、记录时间与整份文件的 SHA-256。该取舍减少对模型服务的依赖，适合先测审核与持久化。自动推断事实需要另外验证推断质量。受审核的文本片段保存在原有来源表，完整材料继续由 Git 或文件系统管理。

每个项目、来源字节摘要和事实键只有一个审核候选。候选 ID 稳定，重复提出返回当前状态。项目、事实键和来源固定，草稿的值、事件类型和生效时间可修改。编辑提高版本号，写操作校验审核者看到的版本。SQLite 串行化写事务。确认时复用正式事件写入，在同一个事务内保存事件、来源、引证及确认状态。

来源时间留在 artifact.recorded_at，事实生效时间放在 effective_at，正式确认时间写入 observed_at。这样可以查询历史有效事实，同时按 known_at 重建确认之前账本知道的内容。对于文件，操作者提供原始记录时间。对于 Git 文件，使用提交者时间。

## 替代方案、兼容和回滚

JSONL 审核记录容易查看，却需要跨文件和 SQLite 协调状态。独立审核数据库也需额外解决同时提交。沿用单库事务可以直接回滚失败写入，并避免两个存储的状态分叉。

新增审核表首次使用时创建，SQLite user_version 和原表结构保留。既有 import、ingest 和 query 的默认接口照常工作。query --with-sources 显式附带证据。既有已批准导入仍使用原入口，审核候选须经 confirm 进入账本。

回退程序版本后，原有查询仍可读取正式事件。若需要连同本版确认的记录一起撤回，先备份现库，再恢复升级前的完整数据库快照。程序回退不会自动删除已确认的项目决策。
