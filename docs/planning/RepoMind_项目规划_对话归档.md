# RepoMind：从 Agent 技术学习到可交付产品的项目规划对话归档

> 归档说明：本文依据当前对话中关于 **“开源项目还是自己做 → 缩小实验范围 → 以 MVP 为 V1 的产品路线”** 三轮规划讨论整理。保留用户原始问题、关键决策、完整路线与验收要求；**助理的长篇答复以忠实结构化整理为主，并非逐字聊天导出**。如果需要逐字记录，应使用 ChatGPT 的官方聊天导出功能。  
> 归档日期：2026-10-26  
> 状态：规划方案，尚不代表软件已经开发或验收。

---

## 1. 技术研究的起点

最初关注的技术与项目：

- Agent 评测及 Langfuse：Trace、Dataset、Experiment、任务成功率和工具调用质量。
- OpenViking：字节火山引擎的 Agent 上下文数据库，资源/记忆/技能组织，L0/L1/L2 逐层加载与搜索。
- Mem0：长期记忆的 ADD / SEARCH、记忆提取、冲突消解、跨会话召回、时间语义。
- Dream-RSI：基于历史探索轨迹、重放模拟器优化探索策略。
- Harness²：通过修改 Prompt、Memory、Tools、Skills、Scripts 等执行系统组件，评估并改进 Agent 工作方式。

后续规划要求：把这些概念变成一个既能实际开发、又有验证指标、还能形成 GitHub 作品集的项目；不只是运行开源仓库或做一次性工具演示。

## 2. 第一轮讨论：开源二次开发还是从零开发？

### 用户原话

> 假如我现在想实际进行这几个知识的项目演练，我是去扒已有的开源项目合适还是自己做一个，假如我要自己做，需要的花费成本多吗，有没有可行性

### 当时的主要建议

- 不建议第一天就复刻全部五个项目，也不建议只 Fork 现有项目、改 UI 后结束。
- 推荐顺序：先运行/了解开源方案 → 独立实现精简核心 → 用成熟组件做对照实验。
- 初始推荐的方向叫 **Agent Memory Lab**，覆盖记忆提取、存储、冲突消解、检索、评测；可进一步连接真正的编程 Agent。
- 为节约费用，用 Python、SQLite、pytest、JSONL 和本地轻量环境；API 模型视需要后引入。
- 钱不是第一障碍；更大的成本是工程复杂度、实验设计、调试和反复测试。
- 早期考虑使用 Mem0 作记忆能力参考，OpenViking 作上下文工程参考，Langfuse 作评测可观测平台；Harness² 和 Dream-RSI 放在后期。

### 第一轮方案的不足

当时的建议把 FastAPI、前端、向量库、记忆系统、评测平台和复杂 Agent 放在了较早的开发范围，容易导致目标分散、配置负担大；且如果没有明确版本闸门，难以保证早期可交付。

## 3. 第二轮讨论：跳过部署、长期记忆是否难以验证？

### 用户原话

> 我的想法不是完全正确你可以进行否定并且给出合理方案。我有一个想法，我们将第一步简化我们省略部署改为详细了解项目的架构工具配置，我们正式的从第二步开始。还有就是有评测这一点还有长期记忆，这个开发的项目会不会验证周期太长，需要的实际开发项目案例太多，我核实的门槛会不会有点高，有没有其他的项目推荐，或者这个项目是可行的，你给我解答下疑惑

### 对疑惑的回答与重要纠偏

1. **认可先分析架构、暂不部署复杂项目**，但要求架构学习有明确时间界限与工程产物。
2. **否定“长期记忆必须等几个月才可以评测”**：可以在几分钟内按时间顺序回放模拟历史会话，快速验证数月跨度的记忆逻辑。
3. **否定“必须开发大量真实项目才能评测”**：初版只用少量虚拟开发项目、结构化事件和几十个有标准答案的问题即可。
4. **认可对验证门槛的担忧**：首先缩小被评测的系统，避免同时调试 Agent、长期记忆、模型输出、前端和工具链。
5. 区分“模拟回放能验证时间/冲突逻辑”和“长期线上稳定性仍需持续运行”，不能把小测试集准确率当作生产级保证。

### 曾讨论的四个候选项目

| 方向 | 内容 | 门槛 | 后续决策 |
|---|---|---|---|
| A. Agent 评测实验台 | 工具调用、Trace、任务成功率、回归测试 | 低 | 评测方法融入 RepoMind |
| B. Agent 长期记忆实验台 | ADD、Search、冲突、跨会话召回 | 中 | 作为 V1 核心 |
| C. 编程 Agent 自我修复 | 工具执行、pytest、错误恢复与 Harness | 中 | 作为 V2 扩展 |
| D. 完整多 Agent 开发平台 | 编排、长期记忆、策略优化 | 高 | 不进入早期版本 |

第二轮阶段名称曾被简化为“Agent Memory & Evaluation Sandbox”，设想几十道题验证小型记忆系统，不做复杂 Web 前端或多 Agent。

### 第二轮的不足

学习与实验路线更加合理，但产品成熟度仍不够：缺乏明确的最终产品定位、版本间依赖关系、每版可交付物、发布标准、代码工程结构和回退机制。

## 4. 第三轮讨论：以 MVP 为 V1，建立正式版本路线

### 用户原话

> 你现在给出的方案确实更加符合我的目标，但是我觉得流程还有项目规划，没有上一次对话的成熟，你现在给我一个推荐项目，并且设计一个方案，用MVP方案作为v1往后推。

### 最终确定的项目定位

**RepoMind — 具备长期记忆与自我评测能力的 AI 开发助手**。

产品目标：面向软件开发项目，持续理解项目技术栈、架构决策、历史任务与当前状态，支持跨会话可靠召回与来源追溯；通过自动评测判断记忆是否改善 Agent 的实际任务表现；后续再研究 Harness 的持续优化。

**版本原则**：每个版本独立可运行、可展示、可验证；不为了最终 V3 的设想让 V1 无法完成。先学架构，不提前部署所有依赖；自研核心，后期以适配器接入 Mem0、OpenViking 等参考实现。

### 项目路线图（最后一次规划的基线）

| 版本 | 名称 | 目标 | 粗略预计投入 |
|---|---|---|---|
| P0 | 架构设计与技术选型 | 开源设计研究、接口和评测方案，不部署复杂依赖 | 1–2 天 |
| **V1.0** | **Memory MVP** | 结构化历史导入、持久化、冲突消解、历史查询、自动评测 | 1–2 周 |
| V1.1 | Intelligent Memory | LLM 提取、语义搜索、记忆冲突辅助分类 | 约 1 周 |
| V1.2 | Evaluation Platform | Langfuse、Mem0 对照、实验可观测性 | 约 1 周 |
| V2.0 | Developer Agent | 真实代码仓库的安全工具执行、跨任务经验记忆 | 2–3 周 |
| V2.1 | Context Engineering | OpenViking 适配、分层上下文、Token 预算与质量比较 | 1–2 周 |
| V3.0 | Self-improving Harness | Harness 候选策略、离线评测、经验重用，参考 Harness² / Dream-RSI | 2–4 周以上 |

时间仅为粗略的个人学习计划，版本是否完成由验收结果决定，不能以时间作为升级条件。

## 6. V1.0 — Memory MVP（正式首版）

### 6.1 用户场景

样例软件项目 CampusRecruit：

1. 2026-01：采用 Spring Boot 3、Java 21、MySQL。
2. 2026-03：**计划**从 MySQL 迁移至 PostgreSQL，尚未实施。
3. 2026-04：明确**已经完成**迁移，当前使用 PostgreSQL。

需要回答：

- 查询 2 月数据库：MySQL。
- 查询 3 月是否完成迁移：否，仍是计划。
- 查询 4 月 10 日当前数据库：PostgreSQL。
- 必须返回对应历史事件、来源或会话 ID。
- 不能把不同项目的记忆互相污染；未知信息应该拒答。

### 6.2 V1 功能与不做的内容

V1 要实现：

- JSONL 结构化事件导入、字段与时间校验；
- SQLite 持久化与重复导入的幂等性；
- 保留原始事件及来源，不简单覆盖历史；
- 计划、完成、纠错、历史状态等规则化冲突处理；
- `project_id + subject/field + as_of` 查询；
- CLI 查询与来源追溯；
- 自动化评测、JSON/Markdown 报告、pytest 测试；
- README 中的可复现运行说明。

V1 **不做**：

- 不接入 LLM，不做智能自然语言事实提取，不做 Embedding / 语义搜索。
- 不部署 Langfuse、Mem0、OpenViking、Redis、云服务器或复杂 Docker 服务。
- 不开发 Web 前端、不实现真实代码修改 Agent 或多 Agent。
- 不直接研究并复刻完整 Harness²、Dream-RSI 论文系统。

原因：先用规则系统建立可靠基线，减少错误来源；V1.1 再加入 LLM 和语义检索，才能明确判断新技术带来了提升还是退化。

### 6.3 V1 技术选型

- Windows 11 本地，Python、Git。
- Pydantic：数据模型和事件校验。
- SQLite：持久化记忆与历史事件。
- pytest：自动化单元和回归测试。
- JSONL：可回放历史事件、评测问答与标准答案。
- CLI：基础交互；先不做界面。
- 代码按 domain / memory / evaluation / adapters 分层。

### 6.5 初版测试规模与实验设计

- 3 个虚拟项目；约 60 条历史事件；48 道评测题。
- 六类题，各 8 道：基础事实、时间推理、状态更新/冲突、跨会话关联、跨项目隔离、未知信息拒答。
- 32 道开发题、16 道独立保留题；尽可能根据项目/模板隔离，防止同构题泄漏。
- 评测内容：总/分类正确率、拒答准确性、来源追溯、项目串用、失败明细和执行时间。
- V1 无 LLM，不能伪造 Token 成本；也不要把结构化检索准确率冒称为语义 RAG 指标。

### 6.6 V1 验收标准

- 程序重启后记忆可读取。
- 同一事件重复导入不会产生错误状态。
- 计划变更不会提前替换当前有效事实。
- 历史时间点查询正确，答案附有来源。
- 不发生跨项目串用。
- 核心状态转换单元测试全部通过。
- 自动生成可阅读和可机读评测报告。
- 可在干净环境按 README 复现。
- 16 道保留测试题的初始发布门槛为至少 13 道正确，但必须披露样本量小的局限。

## 7. V1 后续版本与各自验证条件

### V1.1：Intelligent Memory

- LLM 从自然语言会话提取候选事实，再转为结构化事件。
- 采用 Embedding、向量或混合搜索，提高非精确关键词的召回。
- LLM 可辅助分类 ADD、补充、纠错、计划和完成，但明确区分模型推断与可信来源。
- 评测必须区分提取阶段失败、召回阶段失败、时间/冲突推理失败。

### V1.2：Evaluation Platform

- Langfuse 接入 Trace、Experiment、性能和 Token 成本记录。
- 抽象 `MemoryProvider`，让 Mem0 和自研方案运行同一测试集。
- 公平比较 Recall@K、回答正确率、冲突准确率、延迟和成本。
- 只采用自己复现实验的数据对比，不直接使用其他项目 README 分数进行排名。

### V2.0：Developer Agent

- 接入实际工具：读取/修改代码、运行 pytest、Git diff，工具权限和隔离从严。
- 准备一个可自动验收的样例开发仓库，设计 8–12 个真实开发任务。
- 比较 Baseline（无记忆）、Memory Agent（有记忆）、Enhanced Agent（记忆+时序+经验）的任务完成率、重试率与成本。
- 验证记忆不仅“答对问题”，而且“帮助完成任务”。

### V2.1：Context Engineering

- 研究并接入 OpenViking，比较直接加载、向量检索和目录分层加载策略。
- 指标包括质量、检索耗时、上下文大小和 Token 成本。
- 以质量与成本的权衡来评判分层上下文价值。

### V3.0：Self-improving Harness

- 在有限的参数空间内比较不同工具指导、重试次数、记忆注入时机等 Harness 配置。
- 用固定的开发集进行优化，使用隔离验证集检查泛化。
- 后续参考 Harness² 的候选/探测/组合方法，参考 Dream-RSI 的历史探索轨迹重放思想。
- 不因反复试验训练集就宣称“Agent 自主进化”。

## 8. Git 工作流、版本管理和交付

**版本标签**：

| Tag | 内容 |
|---|---|
| `v1.0.0` | Memory MVP |
| `v1.1.0` | LLM / Semantic Memory |
| `v1.2.0` | Evaluation + Mem0 |
| `v2.0.0` | Developer Agent |
| `v2.1.0` | OpenViking Context |
| `v3.0.0` | Harness Optimization |

推荐 Git 工作流：Issue → Feature Branch → Code → pytest / 评测 → Pull Request → Merge，保持 `main` 稳定；每版保存基线报告与重要 ADR。

V1 开发 Issue：

1. 领域事件与数据校验。
2. SQLite 持久化与幂等。
3. 冲突消解 / 状态投影。
4. 历史查询与来源追溯。
5. 自动化评测与报告。

每个版本交付内容至少包括：源代码、运行说明、测试与评测数据、实验报告、修改记录和已知问题。

## 9. 预算、时间和风险（规划估计）

| 范围 | 估计时间 | 费用思路 |
|---|---|---|
| P0 + V1 | 约 1–2 周 | 本地 Python / SQLite / pytest 可做到 ¥0 软件及模型 API 费用 |
| V1.1–V1.2 | 约 2 周 | 少量模型调用；个人实验预算可控制在约 ¥20–100 起 |
| V2–V2.1 | 约 3–5 周 | 更多 Agent 运行；可先规划 ¥50–200 的试验额度 |
| V3 | 约 2–4 周或更长 | 探索次数增加，单独设置预算和次数上限 |

以上是基于已有电脑的粗略时间和个人预算预留，**不是供应商报价或开发保证**，更不包括人力与新购硬件。

主要风险与控制：

- **范围膨胀**：不提前开发下版本；不因为概念新就加入组件。
- **数据集过拟合**：保留测试集、不同模板和项目，逐步加入真实案例。
- **误判长期记忆能力**：模拟回放验证逻辑，生产稳定性仍需长期运行。
- **冲突处理错误**：区分事件观察时间、生效时间、计划与真正完成。
- **模型随机性**：V1 无 LLM 建立确定性基线，后期用固定评测配置对照。
- **评测不可复现**：所有测试数据、运行命令、指标定义、实验报告进入版本管理。
- **工具权限风险**：V2 真实代码修改在隔离环境进行；不能对真实项目运行不可信自动操作。

## 10. 最终项目决策与下一步

**最终结论**：

> RepoMind 是一个面向开发任务的长期记忆与评测系统，采用“自研小型记忆内核 → 语义智能增强 → 引入成熟评测/记忆框架对照 → 接入真实代码 Agent → 优化上下文 → 优化 Harness”的演进路线。
>
> V1 是能够独立运行、可回放、可评测的 Memory MVP，不需要真实聊天机器人、前端或多 Agent。
>
> 每一版只有通过可复现验收，才进入下一版。

**立刻开展的工作**：先让 Codex 读取本归档及配套的 `RepoMind_Codex_执行提示词.md`，检查本地仓库，完成 P0 四份工程设计，然后实现并验收 V1。后续版本只在得到明确指令时推进。
