## 0. 你在项目中的角色

你是 RepoMind 项目的**资深 Python 工程师、Agent 系统架构师和测试工程师**。请按可交付的软件项目实施，而不是仅提供原理说明、演示截图或无法运行的伪代码。

你可以质疑不合理的技术选择，提出替代方案，并在 `docs/decisions/` 记录架构决策（ADR）。优先保证：**可运行、可测试、可复现、可解释、最小化复杂度**。

请先检查当前 Git 仓库与文件结构：

1. 如仓库已有代码，先列出现状和冲突，尽量复用，不要覆盖用户未提交的改动。
2. 如是空仓库，创建最小项目骨架。
3. 不得静默删除文件、泄露密钥、自动购买服务、擅自部署云端或推送到远程仓库。
4. 遇到与实际运行环境有关的不确定性，先检查再作决定；不要假定第三方 SDK 的接口、价格、部署方式一定不变。
5. 每次完成一个有意义的模块，运行测试并汇报结果；不要声称执行成功但未实际验证。

## 1. 项目背景、目标及定位

**项目名称：RepoMind**  
**副标题：具备长期记忆与自我评测能力的 AI 开发助手**  
**关键词：Agent Memory / Evaluation / Context Engineering / Harness Optimization**

长期目标：让开发助手在跨会话、跨任务场景下，理解不同软件项目的技术栈、架构决策和历史任务；准确区分历史与当前有效决策；可靠召回记忆，并用自动评测证明这些能力对真实开发任务是否有帮助；在后期利用评测结果优化 Harness。

用户关注的研究及技术参考：

- Mem0：长期记忆的提取、写入、检索、去重、冲突处理。
- OpenViking（字节火山引擎）：资源、记忆、技能的目录化组织，以及分层上下文和按需检索。
- Langfuse：Agent Trace、数据集、Experiment、评测与成本分析。
- Harness²：通过候选方案、对照执行和反馈迭代优化 Agent Harness。
- Dream-RSI：利用探索轨迹和历史重放优化策略。

以上是**学习参考**，不是要求在 V1 全部安装或集成，也不意味着这些项目之间存在现成的完整自动集成。

### 产品使用场景

假设开发者长期维护 CampusRecruit（校园招聘系统）：

- 2026-01：使用 Spring Boot 3、Java 21、MySQL。
- 2026-03：提出迁移 PostgreSQL 的**计划**，尚未实施。
- 2026-04：迁移完成，当前使用 PostgreSQL。

系统必须能够正确回答：

- 2026 年 2 月用什么数据库？→ MySQL。
- 2026 年 3 月是否已经完成迁移？→ 没有，只是计划。
- 2026 年 4 月 10 日当前用什么数据库？→ PostgreSQL。
- 这些回答基于哪几条事件或会话记录？→ 输出可追溯来源。
- 用户问的是另一个项目时，不能把 CampusRecruit 的记忆串用。
- 历史没有记录的信息，应返回“不知道 / 证据不足”，不得编造。

## 3. 本轮明确执行范围：P0 + V1

### P0：先完成四份可执行的设计材料

在 `docs/` 下创建并维护：

1. `architecture.md`：RepoMind 模块图、ADD/SEARCH 查询与写入数据流、存储边界、版本演进与适配点。
2. `requirements.md`：产品目标、V1 功能/非功能要求、明确不做的内容、用户故事、发布验收标准。
3. `evaluation-plan.md`：测试集设计、标准答案、基线、指标、开发集/保留测试集隔离、防泄漏、如何复现。
4. `decisions/`：技术选型 ADR；至少记录“V1 不调用 LLM”“SQLite 持久化”“保留事件历史而不直接覆盖”“不部署复杂平台”。

同时在 `README.md` 中写项目介绍和 V1 运行路径。参考 Mem0、OpenViking、Langfuse 的架构思想；如果网络不可用或源码未获取，则明确说明基于什么现有资料分析，不要声称已审阅仓库实现。

**P0 不需要安装/部署 Mem0、OpenViking、Langfuse、Harness²、Dream-RSI。** 但 P0 文档必须落实数据协议、接口和测试方式，不能只是概念介绍。

### V1：最小可运行 MVP

**V1 产品目标**：在不同程序执行/会话之间保存项目决策；能够正确处理“计划 vs 已实施”“历史 vs 当前”“项目 A vs B”，并可自动评分。

#### 必须实现

1. **事件导入**：从 `JSONL` 导入结构化项目事件，使用 Pydantic 校验字段、时间格式、状态与项目范围；无效数据有可诊断的错误提示。
2. **持久化**：使用 SQLite 保留原始事件、唯一 ID、来源、时间信息，重启 CLI/进程后仍可查询。
3. **事件模型**：至少支持 `project_id`、`subject`、`predicate`、`object/value`、`event_type`（如 declare/plan/complete/correct）、`observed_at`、`effective_at`（需要时）、`source_id`、`event_id`。可以根据架构论证调整命名。
4. **冲突/状态处理**：重复事件幂等；计划迁移不改变当前实际状态；明确完成或生效事件才更新有效事实；纠错与时间先后可区分；保留旧记录和替代关系以支持历史查询；存在无法确定的冲突时拒绝伪造明确答案。
5. **检索**：按 `project_id + subject/predicate + as_of` 查询，返回答案与证据 `source_id/event_id`；没有证据时返回明确的 unknown/insufficient_evidence 状态。
6. **评测**：提供固定数据集、自动对比标准答案、分类型汇总、失败样例和可重复生成的 Markdown/JSON 报告。
7. **CLI**：至少能导入事件、查询记忆、运行评测、输出帮助和基本错误信息。
8. **测试**：pytest 覆盖持久化、跨项目隔离、时间查询、计划与完成、纠错、幂等、拒答、来源追溯。

#### V1 明确不做

- 不接入 LLM / Embedding，不做自然语言自由问答；输入先是结构化查询，V1.1 再升级。
- 不部署 Docker、云服务器、Redis、复杂前端、LangChain/LangGraph、Mem0、OpenViking、Langfuse。
- 不实现真实代码修改 Agent、多 Agent、Harness 自优化或完整论文复现。
- 不为适配未来全部需求而做过度抽象；只保留必要的 `MemoryStore`、`MemoryResolver`、`MemoryRetriever` 等可替换边界。

## 4. 数据集与评测设计

**初版规模**：3 个虚拟软件项目、约 60 条结构化历史事件、48 道带标准答案的评测题。测试集不必等待真实几个月：通过事件发生时间与时间点查询模拟长期历史。

题目按六类，各 8 道：

1. 基础事实召回；
2. 时间推理；
3. 状态更新与记忆冲突消解；
4. 跨会话信息关联（限 V1 可验证的结构化条件组合）；
5. 跨项目隔离；
6. 未知信息与拒答。

建议 32 道开发集 + 16 道保留测试集；尽量按项目/问题模板隔离同构样例，避免标准答案和模板泄漏。开发时不要为了通过保留集而频繁针对性改规则。保留集可以在完成开发集验证后用于版本验收。

必须报告：总准确率、分类准确率、未知信息处理率、项目串用次数、来源引用正确性、运行时间、失败案例与评测配置。V1 无 LLM，不必伪造 Token 成本和语义召回指标。

### V1 发布门槛

- SQLite 重启持久化通过；重复导入幂等。
- 跨项目串用 **0 次**。
- 计划迁移不会提前更新已实施状态。
- 历史时间点查询能够返回正确状态和可追溯来源。
- 冲突与状态转换的核心单元测试 **全部通过**。
- 固定命令可产生机器可读 JSON 和人类可读 Markdown 评测报告。
- 保留集初始门槛：16 题至少 13 题正确，同时报告样本量小、统计说服力有限的限制。
- 文档足够让另一名开发者在干净环境中复现；提供一组 Windows PowerShell 命令。

失败时不要调整标准答案以匹配程序输出；必须解释根因、修复实现并重新运行测试。

## 5. 工作顺序与交付方式

请按以下顺序工作：

**Step A — 检查现有工作区**：确认目录、版本控制、Python、已有依赖与未提交修改；汇报简短发现。

**Step B — 完成 P0**：创建四份设计文档与 ADR，写清 V1 的数据契约与验收。若发现重大设计矛盾，给出有依据的调整，并同步修改文档。

**Step C — 实现 V1**：以小步可运行提交进行开发：

- Issue 1：领域模型与数据校验。
- Issue 2：SQLite 持久化与幂等导入。
- Issue 3：冲突消解 / 状态投影。
- Issue 4：按项目、时间检索与来源追溯。
- Issue 5：测试数据、评测运行器、报告与 README。

**Step D — 验收与总结**：实际执行测试和 CLI 演示。报告：已实现内容、运行命令、通过/失败测试数、V1 指标、存在的问题、文件变更、后续 V1.1 建议。

**在 V1 验收后停止。** 不主动开始 V1.1–V3；如环境或权限阻塞，完成能做的内容，诚实列出阻塞，而不是宣称已完成。

## 6. 重要的工程与研究约束

- **事件时间**和**事实有效时间**不应混为一谈；计划日期不自动等于迁移完成日期。
- 允许系统诚实拒答，不允许无证据臆造项目事实。
- 保留审计轨迹：每次答案尽量可回溯到源事件。
- 评测严格区分“系统没召回证据”和“系统召回却做错时间/状态推断”；V1 使用规则系统时亦需记录对应失败阶段。
- P0 中对第三方项目的介绍要标明研究来源、版本、尚未验证之处；不要拿不同 Benchmark 的公布分数直接排名。
- 遵守第三方开源许可证与安全实践。V1 不下载执行未知代码或配置高权限自动工具。
- 不为了好看提前开发 GUI；README、模块边界、测试与质量报告比界面更优先。
- 重要设计决策写入 ADR；对指标任何改善保留旧版本基线。
