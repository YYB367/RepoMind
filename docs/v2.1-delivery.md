# 阶段目标

完成 RepoMind V2.1 上下文工程。让调用方为指定项目选取受预算约束的文档证据，比较直接加载、向量检索和目录分层加载，验证 OpenViking 的 L0、L1、L2 读取契约。

## 运行方法

在源码目录运行以下命令。新环境先安装项目及测试依赖，例如 python -m pip install -e '.[dev]'。当前工作区可使用 ../../work/v2-venv/Scripts/python.exe，并在运行源码前设置 $env:PYTHONPATH='src'。命令示例中的 python 也可替换为该解释器。

~~~powershell
python -m repomind context-select --project cedar-api --query "production canary observation window" --strategy layered --budget 640
python -m repomind context-bench --split dev --budgets 640 1800 --output work/context-dev.json
python -m repomind context-bench --split holdout --budgets 640 1800 --live --output work/context-holdout-new.json
~~~

默认数据在 data/v2.1。命令返回证据正文、来源 ID、访问层级和检索耗时。默认评测用确定性词特征进行离线检索检查。加 --live 才会使用根 .env 现有的 DeepSeek 和独立的 Qwen 配置，并得到实际回答、引用和用量。报告要求一个新 JSON 路径。

OpenViking 在独立环境运行。按官方说明配置本地服务，在指定资源根下准备 project/group/document.md 布局。每个 group 需要有目录摘要与概览，项目、组、文档 ID 使用小写字母、数字和连字符。根 .env 可设置 REPOMIND_OPENVIKING_URL 和可选的 REPOMIND_OPENVIKING_KEY，服务缺省地址为 http://127.0.0.1:1933。用 --corpus 指定同样布局的清单，适配器据此限制读取范围。

~~~powershell
python -m repomind context-select --project cedar-api --query "production canary observation window" --budget 640 --openviking-root viking://resources/repomind-v21
~~~

在 Windows 的独立环境中安装 openviking==0.4.21 后，可从源码根运行真实服务的最小复测。临时实例只监听回环地址，启动时通过原生 RAGFS 写入冻结样例的三个层级，测试结束关闭服务。

~~~powershell
python -m venv .venv-openviking
./.venv-openviking/Scripts/python.exe -m pip install openviking==0.4.21
$env:PYTHONPATH = (Resolve-Path src).Path
./.venv-openviking/Scripts/python.exe scripts/check_openviking_context.py --work-dir work/v21-openviking
~~~

## 技术原理和选型

三种策略共享项目边界和完整记录打包器。直接加载按语料清单排列，例如先读 Cedar 的运行文档，因此小预算下常在到达备份文档前耗尽。向量策略先把项目文档转成数值向量，再计算查询和每条文档的余弦相似度。方向越接近，优先级越高。它能处理部分词语改写，代价是文档索引和每个查询的模型调用。

分层策略用 L0 快速判断目录主题，只进入至多两个候选目录读 L1，再根据条目描述选择 L2。例如问题询问发布观察窗口，delivery 的摘要与问题匹配，概览把 canary 排在前面。三组都把 L2 原文与来源 ID 送进同一个短答提示词。摘要不会作为答案证据。目录覆盖不足或候选条目并列时，原文可能被排在预算之外。

字节预算精确计算实际证据 JSON，包含中文 UTF-8 字节、转义和结构字符。预算不包含系统提示和问题，它们在每组相同。整条证据装不下就跳过。实际 Token 由模型按整条请求报告，表中的 Token 未通过字符比例换算。适配器采用三个标准 HTTP GET 接口，独立于 OpenViking SDK，便于原服务单独维护和部署。[OpenViking 层级说明](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/03-context-layers.md) · [上游内容接口实现](https://github.com/volcengine/OpenViking/blob/v0.4.21/openviking/server/routers/content.py)

## 技术变更、兼容和回滚

V2.0 根据明确的事实键读取事件账本和历史经验。V2.1 另加文档选择入口，服务问答型查询及后续上下文消费方。两个入口分别负责事实时序和文档选择。这里选择运行时内存索引，原因是冻结资料规模小且需要单独测量建索引开销。绑定 SDK 或模型 tokenizer 会增加运行依赖，当前由 HTTP 读取和字节打包承担这两部分职责。取舍、兼容影响和操作说明见 [ADR 0020](decisions/0020-scoped-context-layers-and-openviking-http.md)。

新增 src/repomind/context、两条 CLI 命令、.env.example 中的 OpenViking 可选配置、data/v2.1 的冻结输入以及独立报告。现有 SQLite 和经验库无需迁移。可切换到本地文档选择，或使用 v2.0.0 标记及旧版 wheel 回滚程序。OpenViking 的工作目录由其自身管理。

复测脚本 scripts/check_openviking_context.py 依赖 OpenViking 0.4.21 的测试写入入口以填入人工摘要。实际 RepoMind 适配器使用公开读取接口。真实服务测试验证读路径和项目隔离，三组量化实验使用本地冻结内容，以便各组对照相同版本的证据。

## 实际对照结果

首次保留集共 8 题，其中 7 题有可引用答案、1 题应拒答。短答和引用同时正确才计分。回答使用 deepseek-flash，向量使用 qwen3.7-text-embedding-flash。检索耗时为每组中位数，注入字节为每题均值，输入 Token 为八题总和。

| 证据预算 | 策略 | 短答及引用 | 证据全命中 | 注入字节 | 检索毫秒 | 输入 Token |
|---:|---|---:|---:|---:|---:|---:|
| 640 | 直接 | 2/8 | 1/7 | 487.5 | 0.13 | 1,662 |
| 640 | 向量 | 7/8 | 6/7 | 408.0 | 388.56 | 1,559 |
| 640 | 分层 | 5/8 | 4/7 | 405.4 | 0.13 | 1,552 |
| 1800 | 直接 | 6/8 | 5/7 | 1584.6 | 0.19 | 3,305 |
| 1800 | 向量 | 8/8 | 7/7 | 1560.8 | 411.71 | 3,264 |
| 1800 | 分层 | 8/8 | 7/7 | 956.1 | 0.14 | 2,364 |

1800 字节下，分层在这组题上与向量同为 8/8，少用 900 个回答输入 Token，约 27.6%。640 字节下，分层的两个备份问题被更早的存储条目占用预算，多证据题在三组都无法装入全部所需原文。分层在较小预算下共多读了目录摘要和概览，每题读入约 850 字节，实际只注入 405 字节。向量每次检索包含远程查询 Embedding，本地分层计时只包含本地选取，两个耗时包含的工作不同。

首次开发集共 12 次聊天调用，保留集共 48 次，均无模型协议错误。合计聊天输入 17,153 Token、输出 816 Token。两轮 Embedding 共 23 次请求和 2,633 输入 Token，其中 2,053 用于文档索引。金额未核账。评测代码和冻结语料在首次保留集前记录于提交 ac5366e。原始记录见 [开发集](../reports/v2.1/live-dev-first.json) · [首次保留集](../reports/v2.1/live-holdout-first.json)。

## 回归验收

OpenViking 0.4.21 Windows 实例通过本机 HTTP 验证。CLI 分别读取 Cedar 和 Pine 的 L0、L1、L2，两项目同名 canary 文档返回各自的 12 分钟和 7 分钟规则，预算均在 640 字节内。该测试采用回环开发模式和人工摘要。自动摘要、向量索引和远端鉴权不在这份服务实测回执内。详见 [OpenViking 实测回执](../reports/v2.1/openviking-smoke.json)。

平台环境首轮 pytest 有 465 项通过，4 项真实 Docker 用例因引擎未就绪而跳过。Docker 重启后，使用 V2.0 验收时的同一镜像重新执行这 4 项，全部通过，分别覆盖容器权限、提前退出、超时和输出上限。两次执行共覆盖 469 项不同用例。新增四项测试覆盖项目隔离、多字节精确预算、三层 HTTP 契约、冻结输入保护及 CLI。详见 [首轮 JUnit 报告](../reports/v2.1/pytest-platform.xml) · [Docker 复测 JUnit 报告](../reports/v2.1/pytest-docker.xml)。

## 尚待验证的范围

对照使用人工目录摘要和合成文档，覆盖 2 个项目和 10 道问题。目录层数、摘要质量和文档长度都会影响真实仓库结果。当前报告衡量上下文证据问答，真实代码任务上的完成率仍待实测。向量耗时也受网络影响；八道保留题的结果没有足够样本估计稳定增益。分层读取的项目快照需要随真实资料维护，旧的事实时间语义继续由事件账本处理。
